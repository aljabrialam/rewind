# Feature Specification: Sandbox Capability Contract

**Feature ID**: `000-sandbox-capability-contract`

**Feature Branch**: `main`

**Created**: 2026-08-29

**Status**: Draft

**Business Capability**: External Contract Governance

**Business Actors**: Developer; Continuous integration pipeline

**Input**: User description: "Give the system a single, enforced definition of what the sandbox runtime can do, so no other feature can call a lifecycle operation or read a field that has not been verified to exist on this account."

## Business Context

### Business Goal

Give the system a single, enforced definition of what the sandbox runtime can
do, so no other feature can call a lifecycle operation or read a field that has
not been verified to exist on this account.

### Business Value

The primary failure mode of AI-assisted integration work is confidently invented
method names. The sandbox runtime's fork, pause, and snapshot operations are
available only on certain sandbox classes and certain account tiers, and the
names differ between runtime versions. This feature makes an invented capability
impossible to commit: anything not observed on this account, in this session, and
recorded in the verified capability map fails before it can reach a demo.

### Reference

`.rewind/daytona-capability-map.md` records the verified contract, generated by
`tools/spine_test.py` against the live account. This specification governs how
that record is enforced, not how it is produced.

## Clarifications

### Session 2026-08-29

- Q: When a fan-out requests more sandboxes than the remaining headroom under the concurrency ceiling, what does the port do? → A: Block each over-ceiling request for a bounded wait for a slot to free; if none frees within the wait, fail only that branch with a `capacity` outcome and leave the siblings that were already created intact.
- Q: For an operation to count as verified (and therefore permitted), what must the live run have confirmed? → A: The live run must assert the operation's declared post-condition — its observable effect, such as a fork child carrying the parent's filesystem state or a created sandbox accepting a command — not merely a non-error return. An operation whose post-condition was not asserted is not verified and is absent from the map.
- Q: When the port returns a created sandbox to the caller, what has it guaranteed? → A: The port blocks until the sandbox accepts a trivial command (bounded wait), then returns it. If the sandbox never becomes command-ready within the wait, the port fails the creation and destroys the half-created sandbox; callers never receive a sandbox that is not yet accepting commands.
- Q: When destruction of a sandbox cannot be confirmed, what must the system do? → A: Retry the destroy up to a bound; if still unconfirmed, record the sandbox as an unconfirmed-destroy leak, surface a terminal-class failure, and keep the sandbox counted against the concurrency ceiling until a later sweep confirms it is gone.
- Q: May a declared operation bind to a runtime name the SDK flags as experimental? → A: Only if the capability map records the exact name and its experimental marker, and a contract test pins that exact name so a rename between runtime versions is caught by the drift check.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Invented capability cannot be committed (Priority: P1)

A developer, assisted by an AI tool, writes feature code that asks the sandbox
runtime to perform a lifecycle operation. If the operation was never verified on
this account, the system refuses to start — the failure happens the moment the
code is loaded, long before a demo, a pipeline run, or a review.

**Why this priority**: This is the entire point of the feature. Every other
requirement exists to make this guarantee real. Without it, the project ships an
invented method name to the judges.

**Independent Test**: Reference a lifecycle operation that is absent from the
verified capability map from any feature code, attempt to load that code, and
confirm loading fails with a message naming the missing operation. Reference only
declared operations and confirm loading succeeds.

**Acceptance Scenarios**:

1. **Given** a lifecycle operation that is not present in the verified capability
   map, **When** any code that would invoke it is loaded, **Then** loading fails
   and the error names the offending operation.
2. **Given** a lifecycle operation that is present in the verified capability
   map, **When** code that invokes it is loaded, **Then** loading succeeds.
3. **Given** a declared operation whose required sandbox class is not the class
   of the target sandbox, **When** the operation is invoked, **Then** the system
   refuses the call and reports the class mismatch.
4. **Given** an operation whose live run returned without error but did not
   assert its declared post-condition (for example a fork whose child did not
   carry the parent's filesystem state), **When** the capability map is
   generated, **Then** that operation is not recorded as verified, and **When**
   feature code that invokes it is loaded, **Then** loading fails.

---

### User Story 2 - Full system runs offline with no credentials (Priority: P1)

A developer on a failing venue network, or a continuous integration pipeline with
no runtime credentials, needs to exercise the entire orchestrator end to end. A
second implementation of the single sandbox interface stands in for the live
runtime, behaving equivalently for every declared operation, requiring no network
and no secrets.

**Why this priority**: The constitution's Seam Rule makes this non-negotiable by
13:00. It is how the base test layer stays fast, how the team keeps working when
the network fails, and how a fallback becomes a configuration change rather than a
rewrite.

**Independent Test**: Disconnect the network, provide no credentials, select the
offline implementation, and run the full orchestrator path plus the unit suite.
Confirm every declared operation completes and produces the same observable
outcome shape as a recorded live run.

**Acceptance Scenarios**:

1. **Given** no network and no credentials, **When** the offline implementation
   is selected, **Then** every declared operation completes without contacting
   any external service.
2. **Given** the offline implementation, **When** a declared operation is
   invoked, **Then** its observable result is equivalent to the recorded result
   of the same operation against the live runtime.
3. **Given** the offline implementation configured with a latency value and a
   failure rate, **When** operations are invoked repeatedly, **Then** observed
   delays and failures match the configured values within a tolerance.

---

### User Story 3 - Every sandbox is bounded and always cleaned up (Priority: P2)

Any sandbox the system creates carries an inactivity stop interval and a deletion
interval from birth, and is destroyed when the work that used it finishes —
including when that work raises. The number of sandboxes alive at once never
exceeds the verified account quota.

**Why this priority**: A leaked or unbounded sandbox exhausts the account's CPU
ceiling and stops the demo. Cleanup guarantees and the concurrency ceiling are
cheap to state and expensive to omit.

**Independent Test**: Create sandboxes through the interface, force the using
operation to raise, and confirm each sandbox is destroyed. Start a fan-out that
asks for more concurrent sandboxes than the declared ceiling allows and confirm
the requests that fit succeed, the surplus block for the bounded wait and then
fail with a `capacity` outcome, and the live count never exceeds the ceiling.

**Acceptance Scenarios**:

1. **Given** a newly created sandbox, **When** its creation is confirmed,
   **Then** it has both an inactivity stop interval and a deletion interval
   attached, and it has already accepted a trivial command.
2. **Given** an operation that uses a sandbox and then raises, **When** the
   operation returns control, **Then** the sandbox has been destroyed.
3. **Given** a sandbox the runtime reports as created but that does not accept a
   command within the bounded wait, **When** creation is attempted, **Then** the
   caller receives a creation failure and the half-created sandbox is destroyed.
4. **Given** the number of live sandboxes equal to the declared ceiling, **When**
   another creation is requested, **Then** the request does not increase the live
   count beyond the ceiling.
5. **Given** a fan-out whose requested sandbox count exceeds the remaining
   headroom, **When** it runs, **Then** the requests that fit are created, each
   surplus request blocks for at most the bounded wait and then fails with a
   `capacity` outcome, and every sandbox created before the ceiling was reached
   remains live and usable.
6. **Given** a destroy call that stays unconfirmed after the bounded number of
   retries, **When** cleanup completes, **Then** the sandbox is recorded as an
   unconfirmed-destroy leak, a terminal-class failure is surfaced, and the
   sandbox still counts against the concurrency ceiling.

---

### User Story 4 - Every runtime call is observable and its errors are classified (Priority: P2)

For every call to the runtime, the system records the operation name, the
outcome, and the elapsed time. When a call fails, the failure is classified as
retryable, capacity, or terminal, and that classification is available to the
caller.

**Why this priority**: The contract tests answer "is it us or is it them" in
twenty seconds; that answer depends on knowing which calls were made, how long
they took, and what kind of failure occurred. Classification lets callers back
off on capacity limits instead of treating them as bugs.

**Independent Test**: Invoke a sequence of operations including at least one
success and one induced failure of each class, then inspect the recorded entries
and confirm each carries operation, outcome, and elapsed time, and that each
failure carries the expected classification.

**Acceptance Scenarios**:

1. **Given** any completed runtime call, **When** its record is inspected,
   **Then** it contains the operation name, the outcome, and the elapsed time.
2. **Given** a runtime failure caused by a transient condition, **When** it is
   classified, **Then** it is reported as retryable.
3. **Given** a runtime failure caused by an account or capacity limit, **When**
   it is classified, **Then** it is reported as capacity.
4. **Given** a runtime failure that cannot succeed on retry, **When** it is
   classified, **Then** it is reported as terminal.
5. **Given** a runtime failure whose cause could be transient capacity or a hard
   account quota and the two cannot be told apart, **When** it is classified,
   **Then** it is reported as capacity, never terminal.

---

### User Story 5 - Contract drift is caught in under thirty seconds (Priority: P3)

A developer or pipeline runs the contract tests against the live runtime to
confirm the verified capability map still holds — names unchanged, credentials
valid, tier not throttling. The run completes in under thirty seconds and can be
repeated on demand.

**Why this priority**: Re-run at 15:00, this catches an expired key or a renamed
operation before the judges do. It is a check on drift and credentials, not on
correctness, so it stays small.

**Independent Test**: Run the contract test suite against the live account with a
stopwatch. Confirm it exercises every declared operation, reports pass or fail
per operation, and finishes within thirty seconds. Repeat immediately and
confirm it is re-runnable.

**Acceptance Scenarios**:

1. **Given** valid credentials and an unchanged runtime, **When** the contract
   tests run, **Then** every declared operation is exercised and all pass within
   thirty seconds.
2. **Given** a declared operation whose runtime name has changed, **When** the
   contract tests run, **Then** that operation is reported as failed.
3. **Given** expired or missing credentials, **When** the contract tests run,
   **Then** the failure is reported as a credentials failure and not as a
   capability failure.
4. **Given** a declared operation bound to an experimental-flagged runtime name,
   **When** the contract tests run, **Then** they assert the exact name still
   exists and report a capability failure if it has been renamed or dropped.
5. **Given** a declared operation whose required precondition resource (such as a
   named snapshot) is absent on the account, **When** the contract tests run,
   **Then** that operation is reported as a capability failure, distinct from a
   credentials failure.

### Edge Cases

- What happens when the verified capability map file is missing, empty, or
  unreadable? Loading of any feature code that touches the runtime must fail
  with a message that points at the map, not at the calling code.
- What happens when the capability map declares an operation but omits its
  required sandbox class, its asserted post-condition, or (for an
  experimental-flagged name) its stability marker? The declaration is treated as
  incomplete and rejected at load time.
- What happens when the account tier permits a sandbox class but a required
  precondition resource for an operation — for example a named snapshot — is
  absent? Capability generation does not record that operation as verified, so
  load-time enforcement fails any code that invokes it, and the contract test
  reports it as a capability failure.
- What happens when an experimental-flagged runtime name is renamed between
  runtime versions? The pinned contract test for that exact name fails, flagging
  drift within the thirty-second budget rather than at demo time.
- What happens when the runtime returns an error that could be transient
  capacity or a hard account quota, with nothing to distinguish them? It is
  classified as capacity, and callers treat capacity as "back off; may not clear
  this session," never as a bug.
- What happens when a runtime-issued sandbox identifier is passed through code
  that would reformat, trim, or re-encode it? There is no supported path that
  does so; the identifier is carried verbatim from issue to use.
- What happens when cleanup itself fails after the using operation has already
  raised? The original error is preserved and the cleanup failure is recorded
  and surfaced, not swallowed.
- What happens when a standalone destroy call fails and the sandbox remains
  billable? The system retries up to a bound, then records an unconfirmed-destroy
  leak, surfaces a terminal-class failure, and keeps the sandbox counted against
  the concurrency ceiling until a later sweep confirms it is gone.
- What happens when the concurrency ceiling is reached and every live sandbox is
  still in use? Each new creation request blocks for at most a bounded wait for a
  slot to free; if none frees in time the request fails with a `capacity`
  outcome. The live count never breaches the ceiling, and sandboxes already
  created in the same fan-out are left running.
- What happens when the bounded wait itself elapses for several surplus requests
  at once? Each fails independently with a `capacity` outcome; one surplus
  failure does not cancel or roll back the siblings that succeeded.
- What happens when a contract test run exceeds thirty seconds? The run is
  treated as a failure of the non-functional budget and reported as such.
- What happens when the offline implementation is asked for an operation that is
  not in the verified declaration? It refuses identically to the live
  implementation — the seam does not widen the contract.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-000-01**: The system MUST maintain a machine-readable declaration of every
  sandbox lifecycle operation it is permitted to invoke. For each operation the
  declaration MUST record its verified name, its required sandbox class, the
  observable post-condition that was asserted to verify it, and a stability
  marker indicating whether the runtime flags that name as experimental.
- **FR-000-01a**: The system MUST treat an operation as verified only when a live
  run asserted its declared post-condition — its observable effect, not merely a
  non-error return. An operation whose post-condition was not asserted MUST be
  absent from the declaration and therefore rejected at load time.
- **FR-000-01b**: The system MUST permit a declared operation to bind to a
  runtime name the SDK flags as experimental only when the declaration records
  that exact name together with its experimental marker, and a contract test
  pins the exact name. An experimental-flagged operation recorded without its
  marker MUST be treated as an incomplete declaration and rejected at load time.
- **FR-000-02**: The system MUST expose all sandbox interaction through a single
  port interface, and MUST provide no other path to the runtime. That the port is
  the only entry point MUST be verifiable by inspection — no other module reaches
  the runtime directly.
- **FR-000-03**: The system MUST reject, at load time, any lifecycle operation
  not present in the verified declaration, naming the offending operation in the
  failure.
- **FR-000-04**: The system MUST record the sandbox class required by each
  declared operation, and MUST refuse — before any runtime call is made — to
  invoke an operation against a class that does not support it, reporting the
  class mismatch.
- **FR-000-05**: The system MUST provide a second implementation of the port that
  requires no network and no credentials. For every declared operation its
  observable result MUST match the recorded live result, and it MUST reject
  undeclared operations identically to the live implementation.
- **FR-000-06**: The system MUST preserve every runtime-issued sandbox identifier
  byte-for-byte from issue to use, MUST treat it as opaque with no assumed
  format, and MUST provide no means of constructing, parsing, or altering one.
- **FR-000-07**: The system MUST record, for every runtime call, the operation,
  the outcome, and the elapsed time, and MUST retain those records for the life
  of the session so they can be inspected after a failure.
- **FR-000-08**: The system MUST attach an inactivity stop interval and a
  deletion interval to every sandbox it creates.
- **FR-000-08a**: The system MUST NOT return a created sandbox to a caller until
  it has confirmed the sandbox accepts a trivial command. It MUST block for at
  most a bounded wait for that confirmation; if the sandbox is not command-ready
  within the wait, the system MUST fail the creation and destroy the
  half-created sandbox.
- **FR-000-09**: The system MUST attempt to destroy every sandbox it created once
  the using operation finishes — whether it returned or raised, and whether or
  not creation completed. When a destroy call cannot be confirmed, the system
  MUST retry up to a bound; if still unconfirmed, it MUST record the sandbox as
  an unconfirmed-destroy leak, surface a terminal-class failure, and continue to
  count that sandbox against the concurrency ceiling until a later sweep confirms
  it is gone.
- **FR-000-10**: The system MUST classify every runtime error as exactly one of
  retryable, capacity, or terminal, and MUST expose that classification to the
  caller. Account-quota and transient-capacity failures MUST both classify as
  capacity; when a failure cannot be distinguished between capacity and terminal,
  the system MUST classify it as capacity.
- **FR-000-11**: The system MUST enforce a declared ceiling on concurrently live
  sandboxes, taken from the verified account quota. When a creation request would
  exceed the ceiling, the system MUST block that request for at most a bounded
  wait for a slot to free, then fail it with a `capacity` outcome; it MUST NOT
  cancel or destroy sandboxes created earlier in the same fan-out, and the live
  count MUST never exceed the ceiling.

### Non-Functional Requirements

- **NFR-000-01**: Any lifecycle operation absent from the verified capability map
  MUST fail at load time, not at demo time.
- **NFR-000-02**: Contract tests MUST run against the live runtime and MUST be
  re-runnable in under thirty seconds.
- **NFR-000-03**: Recorded fixtures used by unit tests MUST be captured from live
  runs. Handwritten fixtures are prohibited.
- **NFR-000-04**: The offline implementation MUST support a configurable latency
  and a configurable failure rate.
- **NFR-000-05**: Every bounded wait and bounded retry count in this feature —
  command-readiness wait, ceiling-slot wait, destroy retries — MUST be a declared
  value, not an open-ended loop, and MUST be observable in the call records.
- **NFR-000-06**: The contract test suite MUST distinguish, in its output, a
  credentials failure from a capability failure from a non-functional-budget
  failure (a run exceeding thirty seconds).

### Key Entities

- **Verified Capability Map**: The authoritative, machine-readable record of
  which sandbox lifecycle operations exist on this account, generated from a live
  run. For each operation it holds the operation's verified name, the sandbox
  class that supports it, the observable post-condition that was asserted during
  verification, and a stability marker recording whether the runtime flags that
  name as experimental. It is the single source the load-time check consults.
- **Sandbox Port**: The one interface through which all sandbox interaction
  passes. It has exactly two implementations — one backed by the live runtime and
  one that runs offline — and feature code may reach the runtime through nothing
  else.
- **Sandbox Identifier**: An opaque value issued by the runtime when a sandbox is
  created. It is carried verbatim wherever a sandbox must be named; the system
  offers no way to build, decode, or edit it.
- **Call Record**: One entry per runtime call, holding the operation name, the
  outcome, and the elapsed time. The full set of records is the evidence base for
  drift diagnosis.
- **Error Classification**: The label attached to a failed runtime call — exactly
  one of retryable, capacity, or terminal — made available to whichever caller
  received the failure. Account-quota and transient-capacity failures share the
  capacity label; an ambiguous capacity-or-terminal failure resolves to capacity.
- **Concurrency Ceiling**: The maximum number of sandboxes permitted to be alive
  at one time, taken from the verified account quota and enforced on every
  creation request.
- **Sandbox Lifecycle**: The bounded existence of a created sandbox — born with
  an inactivity stop interval and a deletion interval, command-ready before it is
  handed to a caller, and destroyed when its using operation completes or raises.
- **Unconfirmed-destroy Leak**: A record of a sandbox whose destruction could not
  be confirmed after the bounded retries. It carries the sandbox identifier,
  keeps counting against the concurrency ceiling, and is cleared only when a
  later sweep confirms the sandbox is gone.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of lifecycle operations referenced by feature code appear in
  the verified capability map with an asserted post-condition; any that do not
  cause code loading to fail with a message naming the operation.
- **SC-002**: A developer or pipeline can run the full orchestrator and the unit
  test suite with the network disabled and no credentials present, and every
  declared operation completes.
- **SC-003**: For every declared operation, the offline implementation's
  observable result matches the recorded live result for the same operation.
- **SC-004**: 100% of sandboxes created by the system carry both an inactivity
  stop interval and a deletion interval and are command-ready when handed to a
  caller; 100% have a destroy attempted after their using operation returns,
  including when it raises; and any whose destruction is not confirmed within the
  bounded retries is recorded as an unconfirmed-destroy leak — zero are silently
  assumed gone.
- **SC-005**: The number of sandboxes alive at any moment never exceeds the
  declared ceiling, verified under a fan-out that asks for more; surplus requests
  return a `capacity` outcome within the bounded wait and the sandboxes that fit
  stay live.
- **SC-006**: 100% of runtime calls produce a record carrying operation, outcome,
  and elapsed time; 100% of failed calls carry exactly one classification of
  retryable, capacity, or terminal; and a failure that cannot be distinguished
  between capacity and terminal is classified as capacity.
- **SC-007**: The contract test suite exercises every declared operation,
  re-asserts each operation's recorded post-condition, pins the exact runtime
  name of every experimental-flagged operation, completes in under thirty
  seconds, and can be run again immediately.
- **SC-008**: Every fixture used by the unit suite is traceable to a live run;
  zero fixtures are handwritten.
- **SC-009**: The offline implementation reproduces a configured latency and a
  configured failure rate within a stated tolerance.

## Assumptions

- The verified capability map at `.rewind/daytona-capability-map.md` is current
  for this account and session; keeping it current is the job of
  `tools/spine_test.py`, not of this feature.
- The account's verified quota is a total CPU ceiling of roughly ten sandboxes,
  and the working maximum for concurrent branches is three, per the recorded
  capability map.
- The verified branching mechanism is snapshot-based: a snapshot is taken on a
  live sandbox, and children are created from that snapshot carrying the parent's
  state. The `fork` operation exists on the runtime but returned an unsupported
  error for the sandbox class in use, so its post-condition was never asserted;
  it is therefore not a declared operation.
- The bounded-wait and bounded-retry values (command-readiness wait, ceiling-slot
  wait, destroy retry count) are drawn from the timings recorded in the
  capability map or from configuration; choosing their exact numbers is a
  planning concern, not a specification one.
- A later sweep that reconciles unconfirmed-destroy leaks against the runtime's
  actual live set exists; this feature records the leaks and defines when they
  clear, but the sweep's schedule is out of scope.
- The sandbox runtime is the single declared technology exception permitted in
  this specification, per the constitution; no other technology names are
  implied or required here.
- "Load time" means the point at which feature code is brought into the running
  process, before any demo, pipeline stage, or runtime call executes.
- The two port implementations and the fixture-capture path already have
  placeholders in the repository (`src/rewind/ports.py`,
  `src/rewind/providers.py`, `fixtures/`); this feature defines the contract they
  must satisfy, not their internals.
- Retry, back-off, and queueing policy that consumes the error classification and
  the concurrency ceiling is the concern of downstream features; this feature
  only produces and exposes the classification and enforces the ceiling.

## Out of Scope

- Agent reasoning.
- Checkpoint semantics.
- Any user interface.
- Producing or refreshing the verified capability map (owned by
  `tools/spine_test.py`).
- Retry and back-off behaviour that acts on the error classification.
